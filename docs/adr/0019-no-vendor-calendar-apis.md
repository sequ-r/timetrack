# No per-vendor calendar/task APIs; CalDAV remains the ceiling (#152)

Status: accepted; settles the §19 "proprietary per-vendor APIs only if a concrete user need outlives what CalDAV covers" clause — and [0015](0015-external-readonly-sources.md)'s deferred vendor step — as do not build.

The bar a vendor API has to clear is what already ships: `.ics` file/URL plus read-only CalDAV (`VEVENT` calendars, `VTODO` tasks, `PROPFIND`/`GET` only), account discovery (well-known, principal, home-set, supported components; #150), incremental refresh (sync-collection REPORT, CTag probe, ETag conditional GETs, in-place reconcile, withdrawal of still-pending suggestions on remote delete; #151), secrets in the OS credential store behind an injectable seam (#149), windowed RRULE expansion in core (−31d…+93d, wall-clock across DST), and the read-only suggestion model (fetching never creates an entry, confirmed entries record the external UID). A vendor integration must serve a concrete user workflow this stack cannot — and none exists with evidence today.

Google Calendar/Tasks fails that bar on cost, not on fit. Read-only scopes map cleanly onto the suggestion model, and the Tasks API would reach the one Google surface CalDAV cannot (Google Tasks has no CalDAV; Google Calendar does). But the price is a second identity platform beside the app: a Cloud Console project, an OAuth consent screen with verification for sensitive scopes, a localhost-redirect browser loop in a local-first app, and a refresh/revocation lifecycle to carry forever — refresh tokens persist until they do not (revoked, expired, quota-exhausted), and every failure mode needs UX. Incremental calendar sync exists (list syncTokens), but push (watch channels) demands a public HTTPS endpoint the service will never have. Recurrence buys nothing — the API expands instances server-side, which core expansion already equals for suggestion purposes — while Tasks semantics (flat lists with subtasks, no `VTODO` parity for status/recurrence) need their own mapping, quota/rate-limit handling, and a deprecation watch, all for one provider's task lists.

Microsoft Graph/Outlook fails the same bar harder. It holds the one genuine reach gap: Microsoft 365 mailboxes have no supported CalDAV path (basic-auth retirement closed the door CalDAV never properly opened), so Outlook calendars and To Do lists are unreachable today. But Graph's auth burden exceeds Google's: Azure app registration, per-tenant delegated-permission consent with possible admin consent and Conditional Access refusals, an MSAL token cache with refresh, and throttling (`429` + `Retry-After`) as a way of life. Incremental sync means delta queries; subscriptions again need a public HTTPS endpoint plus renewals. Task semantics split across the legacy Outlook-tasks and To Do APIs (checklists, no `VTODO` recurrence parity), recurrence-instance expansion adds nothing over core expansion, and distribution gains publisher verification and permission-review overhead. It fits the suggestion model — read-only delegated scopes exist — but it buys one provider's mailbox at the cost of an enterprise consent platform.

So the decision is to build neither, and to build no anticipatory generic OAuth layer either: an auth framework without a user workflow is maintenance without a customer. The §19 rule stands as written — vendor APIs only on a concrete surviving need — with these revisit triggers, each sufficient to reopen the question for the named provider only: a provider removes or breaks the CalDAV path TimeTrack relies on and a named user workflow breaks; a user files a concrete workflow needing Google Tasks or Outlook/To Do content unreachable via CalDAV/`.ics`, with the calendar or task list named, which becomes a provider-specific follow-up issue with that workflow as evidence; or authentication changes (password/app-password removal) make CalDAV login unusable for a major provider — in which case OAuth-for-CalDAV (XOAUTH2 on the same transport) is evaluated before any vendor API, since it keeps one protocol.

## Considered Options

- **Build the Google Calendar/Tasks integration now.** Rejected: the only unreachable surface is Google Tasks, and one provider's task lists do not justify an OAuth platform, a token lifecycle, a second task-semantics mapping, and verification overhead.
- **Build the Microsoft Graph integration now.** Rejected: the reach gap is real but hypothetical — no user workflow with evidence needs an Outlook mailbox today — and Graph's registration, consent, throttling, and versioning burden is the heaviest of the options.
- **Build a generic OAuth/token layer in anticipation.** Rejected: refractors nothing that exists (CalDAV authenticates with stored passwords, #149), serves no current workflow, and still needs per-provider semantics when a real trigger arrives.
