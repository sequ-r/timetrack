# The service owns the timezone; the core owns parsing

A typed local time (`09:30`, `2026-03-29`) has exactly one owner at each step. The service is the single timezone authority: it resolves its zone strictly from `TZ` or the system zone (`Tz::try_from_env` — an unusable zone stops it at startup, never a silent UTC or fixed-offset guess), refreshes that resolution live so a system-zone change is picked up without a restart, and reports the zone **name** on every snapshot. `timetrack-core` is the single parsing implementation (`parse_moment`, `parse_anchor_day`), and clients may run it only with the zone the snapshot name strictly resolves to (`Tz::from_snapshot`); a nameless or unusable snapshot zone is an explicit client-side error, not a fallback. On clock-change days the parser resolves the typed wall clock in the zone (not elapsed-since-midnight): a skipped spring-forward time is refused and a repeated fall-back time reads as its first occurrence.

## Considered Options

- **Send the typed string to the service and parse there.** Rejected: the GUI validates dialogs synchronously on the UI thread, which must never touch the bus (the service connection lives on its own thread), so service-side parsing would close dialogs optimistically and surface typos as late footer errors instead of inline ones. It also buys nothing here — every client runs on the same machine, on the same system clock, bundled in the same AppImage with the same core parser, so the only possible divergence was *which zone* a client parsed with, and this ADR pins that to the service.
- **Send the named zone alongside each parsed instant for the service to check.** Rejected as redundant once clients can only obtain a zone from the service's own snapshot: the check could only ever compare the service's name against itself, while adding a field to every mutating call.
