# A typed D-Bus interface, dual-served through the transition

Every method on `org.sequ.timetrack.Entries` returned one JSON string, and refusals travelled as JSON inside a `Failed` error body — no introspection value, errors legible to no tool, and the snapshot's JSON grows with total history (5.5 MB at the measured 10-year workload of 36,530 entries). Now the same object also serves `org.sequ.timetrack.Entries2`: the same methods with typed arguments and struct replies (`Snapshot2`/`Entry2`/`Project2`, twins of the JSON views, differing only where D-Bus has no `Option`), one error mechanism — named errors mirroring `ServiceError` variant for variant with typed bodies (`WireError`, hand-implemented because the derive assumes a free-text first field) — and `ApiVersion` returning 2 as the discriminator clients probe. Clients in `timetrack-proto` probe it once at connect, speak typed when it answers, and otherwise use the legacy interface unchanged, mapping both back to the same types — so old clients work against new services, new clients against old services, and the only legibility question left is which side an ancient binary belongs to, which the interfaces it answers on settles.

On snapshot size: the snapshot stays whole in v2, deliberately. At the 10-year workload it is 3.2 MB typed versus 5.5 MB JSON — far inside the bus's 128 MiB message ceiling — and clients genuinely consume all of it (entry lists, export previews). Windowing would be a feature change disguised as a signature change; if a future workload makes it necessary it gets its own issue. The legacy interface is transitional: it is kept while one release cycle of AppImages and host builds can still meet across it, and its removal is filed as follow-up work (#129) rather than left as a silent second contract.

## Considered Options

- **Hard cutover to the typed interface.** Rejected: clients already in the wild cannot be taught which side is older after the fact — against a typed-only service they could only print today's "different versions" message, and a leftover old service would break new clients the same way. Dual-serving costs one extra interface impl over the same core, and buys a window where every pairing works.
- **Typed replies with `Failed`+JSON errors kept.** Rejected: two error mechanisms is exactly what #110 exists to end, and tray/GUI recovery pattern-matches refusal variants — a name per variant with typed fields is the typed equivalent, not a message to re-parse.
- **Window the snapshot now (totals plus recent entries, queries for the rest).** Rejected for this change: measured size does not force it, and it would reshape what the Home list and export preview can show — a product decision riding on a signature migration is how both go wrong.
