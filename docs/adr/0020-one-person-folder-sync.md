# One-person sync over a user-held folder, snapshots plus last-writer-wins (#161)

Status: accepted as the design; no implementation ships in this wave — the build is split into the follow-ups below, none started. Settles the §20 "sync itself remains undesigned" clause on top of the UUID identity [0018](0018-uuid-ids.md) landed.

Sync travels through a folder the user already replicates — Syncthing, Nextcloud, Dropbox, iCloud Drive, a USB stick, an NFS share, anything that moves files between the person's desktops. Star topology through that folder: no TimeTrack server, no account, no new network protocol (§12 and §16 local-first stand unchanged). One file per device, named by its random `device_id`; each device writes only its own file (atomic temp-write plus rename), so the file layer can never hand us a conflict copy of our own data, and reads every peer file. The merge layer sees only envelopes, so a later LAN transport could carry the same bytes without touching ordering rules — but no second transport ships in the first slice.

Each file is one encrypted envelope: format version, writer `device_id`, `published_at`, a `merged_through` watermark, and the writer's full merged state — entries, projects, external-source configs, tombstones — every record already carrying (`updated_at`, `device_id`). Snapshots, not an operation log: one person's ledger is kilobytes, so every device republishes everything it knows and a newcomer bootstraps from any single fresh file. Merge is idempotent and order-free; sync files are derived artifacts, deletable and republishable at any time. Envelope versioning follows the §2 rule: newer than the binary is refused loudly, corrupt files are ignored with a warning, last-good state stands.

Ordering is per-record last-writer-wins on (`updated_at_ms`, `device_id`), greater `device_id` breaking timestamp ties — deterministic on every device given the same files. Deletion joins the same ordering as (`deleted_at`, deleter `device_id`): a tombstone beats versions at or below it, an edit strictly newer resurrects the record. Concurrent edits are rare (one person, two keyboards) but never silent: the losing version lands in a local conflict journal, listed in CLI/GUI, restorable by re-saving (which stamps a fresh `updated_at` and wins the next merge); the journal never syncs and never auto-deletes. Wall-clock skew can only misorder edits made on two offline devices inside the skew window, and the journal bounds that damage to a reviewable row.

A tombstone compacts only once every paired peer's `merged_through` has passed its `deleted_at` — the watermark ("this writer has merged every peer envelope published at or before T") proves the delete is everywhere. A peer whose envelope is older than the 90-day horizon is departed: its file stops blocking compaction and is quarantined from merging until re-paired. A device returning from beyond the horizon (or from a restored old backup) pulls and merges before its next publish, so its pre-delete versions can never outlive a compacted tombstone; until its watermark is fresh, peers quarantine its file. Re-pairing is one action — drop the stale file, reseed from merged state — and local-only writes made while departed survive it, because merging precedes publishing.

External-source rows sync as ordinary records, but two gaps close first: source ids are `src-{rand}` today, and `remove_source` leaves no tombstone — so sources remint to UUIDv4 ([0018](0018-uuid-ids.md)'s migration shape, suggestions' `source_id` follows) and removal tombstones `kind="source"`. Secrets never sync: `cred_ref` stays a per-device pointer into that device's OS store (#149), each device holding its own CalDAV password. Suggestions, `caldav_sync`, and `caldav_resources` are per-device fetch caches and never sync; each device fetches independently. That leaves one model gap: a confirmed `External` entry carries no external UID today (the UID sits on the per-device suggestion row), so peers would re-suggest confirmed events — confirmed entries must carry (source UUID, external UID) in synced state, and the fetch path dedups against synced entries, not just local suggestions. Dismissals stay per-device: what one device dismisses, another may still suggest. Accepted and documented; syncing dismissal keys is deferred.

Offline is the default state the design never punishes: the service never blocks on sync, and every single-device behavior works identically with sync off, on, or broken. Pairing: on the first device, enable sync and pick the folder — a sync key generates into the OS store and the first envelope publishes; on the second, point at the same folder, enter the key, pull-merge, publish. Enabling sync on a single-device store IS the migration — the first publish seeds it, no other step. Unpairing stops publishing (optionally deleting the device's file) and touches no local data.

Backup is unchanged (§17: copy the database while stopped, or the CSV pair) — and the sync folder is explicitly not a backup: conflict losers live only on the losing device, compacted tombstones are gone, quarantined files hide records. The README will say so. Restoring a database backup older than the horizon follows the returning-device rule: merge before publishing.

Envelopes are XChaCha20-Poly1305 ciphertext under a random 256-bit sync key (pure-Rust crypto, no new runtime); the key lives in the OS credential store behind the #149 seam and crosses to a new device only at pairing, out of band (a typed code in the first slice, QR later). The file host sees opaque blobs with random-hex names plus sizes and mtimes — no entries, projects, locators, or usernames. The trust model is one owner and their own machines: no per-device ACLs, no signatures beyond the AEAD, no multi-user sharing (still refused). Losing a device means deleting its file and rotating the key — re-pair the survivors and the old ciphertext goes dark.

## First shippable slice and follow-up work (named here, not filed)

The shippable slice is CLI-usable sync between two machines: envelope format plus encryption plus key storage; source UUID remint plus source tombstones; snapshot publish/pull/merge plus conflict journal plus a `sync` CLI surface (enable/status/now/unpair); confirmed-entry UID carriage plus fetch dedup. Hardening follows: tombstone compaction plus departed-peer quarantine plus re-pair flows; then GUI pairing/status/conflict review and the README recovery runbook. The follow-ups, in build order:

1. **Sync envelope format, encryption, and key storage** — envelope schema and versioning, XChaCha20-Poly1305 seal/open, sync-key lifecycle on the #149 credential seam, newer-than-binary refusal.
2. **Source UUID remint and source tombstones** — `src-{rand}` to UUIDv4 migration with suggestion references following, `remove_source` tombstoning `kind="source"`.
3. **Snapshot publish/pull/merge, conflict journal, CLI surface** — per-device files, LWW merge, local conflict journal with restore, `sync enable/status/now/unpair`; two-device CLI sync is the acceptance proof.
4. **Confirmed-entry UID carriage and fetch dedup** — (source UUID, external UID) on synced `External` entries, fetch skipping already-confirmed events cross-device.
5. **Tombstone compaction, quarantine, and re-pair** — watermark-plus-horizon compaction, departed-peer quarantine, pull-before-publish, one-action re-pair.
6. **GUI pairing/status/conflict review and recovery docs** — enable/show-code/enter-code, sync status and stale-device warnings, conflict review, README backup-versus-sync section and recovery runbook.

## Considered Options

- **Hosted TimeTrack server/account.** Rejected: a §12 non-goal, a service to run and a credential database to protect, for a ledger that never needs a vendor in the loop.
- **LAN/mDNS direct sync.** Rejected as the only transport: needs both devices online and mutually reachable, which fails the laptop-away-from-home week; stays possible later behind the transport-agnostic merge layer.
- **One shared database file on a cloud drive.** Rejected: multi-writer SQLite is the world the service exists to prevent ([0014](0014-sqlite-store.md)); lock files and conflict copies would corrupt history.
- **One shared envelope file.** Rejected: every device writes it, so the file layer's conflict copies become our merge problem; one file per writer removes the case by construction.
- **Operation log / CRDT.** Rejected: a low-write-rate personal ledger fits in snapshots; a log buys per-peer knowledge vectors and log compaction for a problem measured in kilobytes.
- **Syncing secrets, suggestions, or fetch caches.** Rejected: secrets stay in per-device OS stores by §19's rule; caches are re-fetchable, and syncing them would fork fetch state across devices.
- **Silent last-writer-wins.** Rejected: deterministic, but a concurrent edit would vanish without a trace; the conflict journal keeps determinism and the data.
